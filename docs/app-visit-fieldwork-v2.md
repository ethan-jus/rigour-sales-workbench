## 已实现合同

- Foundation 维护选项：营业状态、经营类型、业务线、意向、合作状态，以及新增沟通结果、未接触原因、后续行动、接待人角色。业务线与已有经营类型沿用实际 AUTO 编码，不用原型 DEMO 编码，不写客户端名称数组。
- 页面是一张滚动表单：门店现状、本次沟通、现场照片、后续跟进、补充记录。已知门店资料带入；未知字段不默认“营业中”或“高意向”。已合作独立于意向等级，各业务分别采集。
- 接待人在当前页底部面板新增，姓名或称呼、角色必填，电话和微信线索选填。保存后自动选中；不跳转、不清空拜访表单，保存中防重复点击。手填微信线索不伪造企微正式建联。
- 必填星号和字段校验一致；提交时标出缺项并滚到首个错误。停业需依据，“其他未接触”需原因，跟进行动与日期成对填写，照片沿用本次规则数量。服务端重新核验字典、归属、接待人和照片，错误原因通过统一 API 显示。
- 草稿继续按环境 / 租户 / 账号 / 采集 ID 隔离。切换沟通结果时不提交隐藏的接待人或业务信息；门店 revision 变化时需重新确认状态与类型，其他输入保留。
- 录音主行显示本次累计时长。5 分钟分段仅用于文件保存与上传；累计取本机 / 服务端同 clip ID 的并集，避免上传后重复相加，再加正在录制的未登记时长。中断空档不计入，恢复与返回页面后继续累计。实际录制累计与服务端“已核验”分开，历史文件导入不计现场录制。
- 自动离店距离加入 Sales 已有 CaptureRules，独立于到店半径；开启自动离店时不得小于到店半径，范围 1–5000 米。旧版本未设值时沿用到店半径；发布新版本不改进行中拜访快照。自动离店仍保留原有精度、连续采样和定位恢复逻辑。

| 内容 | 写者 / 存储 |

| 选项和版本 | Foundation，既有租户字典表，新增 V60 |

| CRM 观察快照 | CRM，`crm_visit_fieldwork`，新增 V38；保存字典名称、接待人快照、来源和同步状态 |
| 门店营业状态 | CRM 既有统一门店及状态变更链，沿用 `crm:store:status-write`；停业关闭继续原生命周期规则 |
| 门店经营类型 | CRM，`crm_store_master.business_type_code`；与行业分类分开 |
| 各业务最新观察 | CRM，`crm_store_business_progress`；按租户 / 门店 / 业务唯一，保留来源拜访 |

Sales 在同一事务内保存采集结果和既有 `CrmVisitEvidenceChanged` outbox。CRM 使用原投递重试链处理：先核对身份、版本和当前归属，再保存观察并回写门店；冲突只保留观察，显示 `CONFLICT`，不覆盖较新资料。重复提交不重写首次提交时间，重复消息不重复变更门店。

销售选择“已合作”是现场业务关系观察，不替代订单、合同或业务开通事实，不凭点选改变正式合作客户池、成交或业绩。`UNKNOWN` 不清空已知门店事实，暂无意向也不删除已有业务事实。

旧拜访没有结构化结果时保留历史摘要和整体意向展示；新拜访使用提交时冻结的字典名称显示历史，字典以后停用或改名不改变原记录。

## 缓存与读取

- Foundation 使用现有 `shared-cache` / Redis，键包含租户、字典代码、GLOBAL 与租户覆盖版本；读前仍核验权限。写事务绕过缓存，回滚不污染缓存。沿用单飞、容量上限及 Redis 故障回源。
- 新增有效字典批量端点 `GET /api/v1/business-settings/dictionaries/effective-batch`，CRM 一次读取现场需要的 9 本字典。新增 `GET /crm/stores/{store}/visits/{visit}/fieldwork` 与 `GET /crm/stores/{store}/fieldwork-profile` 聚合表单与门店画像。
- Sales `PUT /sales/me/visits/{capture}/result` 携带 fieldwork；内部先调用 CRM 校验，再本地事务持久化。`GET /sales/me/visits/{capture}/fieldwork` 返回本人已接收快照。
- CRM 回写调用既有 `QueryCache.changed`，提交后使门店、公私海、合作及附近查询版本失效；App 提交后也失效现有客户显示快照。门店详情进入时读取最新画像。
- 规则仍复用 `visit-policy.uts` 和 Sales 现有缓存。页面基础数据与材料分组并行；定位监测初始化不阻塞表单。
