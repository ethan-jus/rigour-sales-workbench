# 工作台首页 · 业务概览方案 V2

2026-11-11。根据用户最新反馈重新设计；本轮只交付设计原型，不替换 `app/pages/home/home.uvue`。原型所有金额、客户、订单与待办均为示例。

## 设计目标与取舍

销售一眼看清自己的交易进展、还有多少钱未收、今天的订单与回款，再进入具体工作。简洁指去掉废话和重复说明，不是删掉业务功能。沿用登录页的白底、石墨文字与品牌橙。

取消上一版“金额未接通就不设计”的原则；设计体现完整业务需求，开发时解决接口与归属问题。首页不放营销欢迎语、说明卡、虚构增长率、无口径的目标进度或佣金。

## 视觉方案

- 白 #FFFFFF：主体；石墨 #252A31：正文、金额；灰 #626970：次级信息；品牌橙 #C64C1C：待回款与主要入口；灰底 #F5F6F7：分区；浅橙 #FFF2EA：重点区域。
- 系统中文字体（PingFang SC / Microsoft YaHei / 系统 sans-serif），金额等宽数字。页面标题 22，主金额 36，次金额 22，区块标题 17，正文 14–15，次级 12–13。
- 手机左右 20px，区块 20–24px，内部 8–16px；金额左对齐，同组基线对齐。只给月度概览一个主容器，今日数据与快捷入口留在白色平面，待办用行分隔。
- 核心视觉为月度金额与橙色待回款的对照；不加渐变、装饰图表、通用彩色九宫格或大阴影。图标统一线宽。
- 每个入口至少 44px。长客户名可换行，不挤掉金额；底部沿用现有五个 Tab。

## 布局比较与选择

比较“六个等大的数字卡片”与“月度概览 + 今日一行 + 行动区”。前者让所有指标一样重，重复旧版碎片卡片问题；选择后者：一个业务总览、一个时间分组、一个行动区。交易额大，待回款用橙色，今日数字适度缩小，拜访入口仍能在第一屏找到。

## 数据与入口

所有指标限定当前销售身份与租户，不能把管理员可读范围当成本人业绩。汇总与列表使用同一过滤口径，不能累加第一页代替全量总计。

| 首页信息 | 拟定口径 | 点击目标 |
|---|---|---|
| 本月交易额 / 订单数 | 当月有效销售订单的应收金额 / 笔数；草稿、取消、删除排除，退款净额沿用平台最终统一口径 | 订单，本月、本人 |
| 本月回款 | 当月发生并按平台确认状态计入的回款；允许对应以前月份订单 | 订单内的回款明细，本月、本人归属 |
| 累计待回款 | 本人所有有效订单当前未收金额合计，包含以前月份 | 订单，待回款、全部日期 |
| 今日订单 / 交易额 | 今日有效订单数 / 应收金额 | 订单，今日、本人 |
| 今日回款 | 今日发生且符合确认口径的回款 | 订单内的回款明细，今日、本人归属 |
| 待出库 | 有效订单的待出库 / 部分出库状态，数量为订单笔数 | 订单，相同出库筛选 |
| 待拜访 | 今日拜访计划中未完成项 | 今日拜访计划 |
| 开始拜访 / 查客户 / 查商品 / 拜访计划 | 复用现有能力和权限 | 对应业务页 |

“本月回款”不是“本月创建的订单截至现在已收金额”；“收款人”也不是“销售归属人”。“累计待回款”不是逾期；未核实账期不展示逾期标记。交易额也不等于绩效：当前 BI 的收齐业绩另有“订单首次收齐日”口径，本设计不把二者混称。

## 待回款钻取

首页金额或待回款标签 → 待回款列表（全部日期） → 订单详情。

列表顶部显示未收合计与订单数；可搜客户 / 订单号，切换全部待回款、未回款、部分回款。每行优先显示客户名和未收金额，再显示订单号、日期、已收 / 订单金额。部分回款可辨识，但不使用警报式红色。详情展示应收、已收、待收和回款记录，不把上传凭证当成财务已到账。

首页默认只预览两项，更多内容到列表。待办分类切换不改变上方月度统计口径；返回首页恢复原分类。购物 / 拜访草稿与异常上传只在有真实未完成任务时出现，不常驻空卡片。

## 现有接口与待实现边界

核对了当前相邻供应链仓库的 Order 与 BI 源码：

- `OrderSalesOrderApi` 已有列表与 `/api/v1/orders/sales/totals`，含日期、销售归属、订单 / 回款 / 出库状态过滤；汇总 DTO 有 payableAmount、paidAmount、unpaidAmount、total。
- `OrderSalesPaymentRecordApi` 提供按回款时间查记录，但 collectorStaffCode 是收款人，不可直接当本人销售业绩过滤。
- `SupplyDashboardQueryMapper` 已有回款事实与归属、receiptDetails 聚合，以及独立的 fullyPaidPerformance 口径。现有回款明细查询是否完整执行财务有效状态规则，需在接入时对齐，不能仅按 DTO 名称判定。
- App 当前 Orders 只有订单状态筛选；本方案需要补日期、回款 / 出库筛选与对应聚合接入，并核实服务端当前销售身份绑定。不是改几个数字就已完成。
- 尚未进行真实接口、权限范围、金额勾稽或原生实现验收。该原型不访问服务端、不签到、不写订单或收款。

## 原型与验证

原型：`outputs/app-ui-20261111/home-business-v2.html`。独立静态设计文件，仍在原项目目录内，无新工程或 worktree。

原型只实现首页、待回款钻取、筛选搜索与只读订单详情。其他入口点击后标明设计中的跳转目标，不伪装成已上线业务。正式页面不包含这些原型提示。

数据状态：加载时保留数字位置并显示占位；真实空数据为 0。请求失败使用短提示与重试，不伪装为 0；无权限时隐藏对应业务入口。用户切换、租户切换时清除上一身份数据。

验证记录（2026-11-11）：
- 375 × 812 下首屏显示完整月度概览、今日三项、四个入口与两条待办；320px 宽度无横向溢出，纵向可滚动。
- 原型待回款 12 笔 / ¥42,780；未回款 6 笔 / ¥16,680，部分回款 6 笔 / ¥26,100，汇总一致。
- 客户搜索、无匹配状态、详情回款记录、返回保留筛选和搜索、首页待办切换已通过浏览器操作检查。
- 订单详情隐藏底部 Tab，保留返回；首页和订单列表保留 Tab。
- 原型 JavaScript 语法检查通过。无业务页面代码改动，本轮未做原生编译或真实接口验收。
- 截图：`home-business-v2-375.jpg`、`home-receivables-v2-375.jpg`、`home-order-receipts-v2-375.jpg`（均在原型同目录）。

后续实现：金额保留真实精度；首页超过容器宽度的金额可统一使用“万”并明确单位，明细展示完整金额。需要校验大金额、长客户名、字体放大、安全区和原生权限；不把本轮 Web 原型检查当成真机验收。
