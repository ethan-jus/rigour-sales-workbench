# 外勤记录 V3：数字就是门店标记

2026-11-17，用户已批准并实施页面；原生验收与待办见 `docs/qa/fieldwork-v3-20261117/验证记录.md`。下文“里程真实查证”保留设计阶段的时间点事实。承接用户最新澄清：1、2、3 是直接替代定位图钉的图标，不是在地图旁边增加“拜访1–11”文字标签。前一版误解以本稿纠正。

## 最终视觉与交互要求

- 地图门店用品牌橙数字圆标、白字与白色细边。示例1、2、3，与时间记录同号；不是 emoji，不叠加普通定位图钉，不常驻门店名称大标签。
- 只写“签到”“签退”，删除所有面向用户的 GO/END。地图用绿色圆点和红色方点区分起终点，图例在地图之外。
- 删除“作业时段”、两套路线页签、重复的当前事件卡、左右翻页。
- 页面结构：日期 → 拜访里程/次数/累计停留 → 单一地图 → 时间记录。
- 路线使用细线与方向箭头，数字明确先后；有实际定位数据时按有效定位段绘制，缺失不拼接成假道路。
- 全屏只放大同一张地图；选中具体时间段才突出一段方向，其余淡化。同路往返按发生时段区分，不额外画两条平移线制造两条路的错觉。
- 每个记录包含时间、中文门店名/打卡类型、地址；拜访显示起止时间、停留和查看详情。已取消拜访不进入正式拜访计数、编号与里程链条。
- 同址重访仍占真实时间序号。正式实现需补“同位置多序号”交互：同一锚点紧凑展开各次数字，点击对应记录选中该次，不移动真实坐标，不把 1–11 当作大文本覆盖地图。本稿主画面使用三家不同门店，不能宣称同址情形已真机验证。

## 里程真实查证

本轮对 DEV 数据库只读查询（事务 READ ONLY），查询当前 Redmi 已展示的2026-11-17 10:04签到工作日，唯一匹配：

| 项目 | 真实结果 |
| --- | --- |
| 工作日 | ACTIVE，尚未签退 |
| 轨迹采样表 | 0行 |
| 定位会话 | ACTIVE，point_count=0 |
| 定位规则 | 启用，采样周期20分钟 |
| 已完成拜访 | 3次 CHECKED_OUT |
| 已取消拜访 | 8次 CANCELLED |
| 系统定位 app-op | FINE_LOCATION allow；不足以证明后台采集已运行 |

因此此前“11次拜访”包含了8次取消，数字和地图序号都不应照搬。当前没有轨迹点，不能从签到、门店几个地点反推出全天真实路程。

同时确认独立的规则冲突：App按 `locationIntervalMinutes*60` 秒节流，后端 `SalesTrackMetrics` 用最大300秒的连续性阈值。20分钟周期超过5分钟，即使后续点正常上报也会被拆成不连续片段。该冲突需要结合产品采样约定统一解决；不能只改前端文案或扩大阈值伪造完整道路。

零点的上游具体原因（记录同意、采集状态、会话恢复、上报）尚未定位完成。此次没有开启/修改轨迹同意，没有写数据库、调整采样规则或重启服务。不要把“已查证零点”表述为“已修复采集”。

## 缺数据的合理表达

- 有有效记录：展示实际已记录的里程；有缺口则标注“已记录”，不称全天完整。
- 没有轨迹点：不显示一格无意义的“无法计算”或0公里，显示已知拜访次数和停留；在地图前给出具体事实“今日尚未记录行程”与“检查记录状态”恢复入口。真实门店数字点仍可查看，隐藏不存在的路段操作。
- 历史缺失路程无法补造成真实轨迹。若以后需要门店间导航估算，必须作为明确标注的估算口径另行确定，不能默默替换实际里程。
