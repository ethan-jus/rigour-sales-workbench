# 拜访现场 V2 设计方案

2026-11-16。设计已获用户确认，原型使用示例数据，不会调用实际业务接口。下文保留设计阶段口径；实施状态与真实验证见 [实施与验收](../../../../docs/app-visit-fieldwork-v2.md)。

- [可交互总览](index.html)：门店与沟通、照片与跟进、业务进展面板；顶部可切换拜访规则。
- [手机原型](prototype.html)：同一张滚动页面，支持营业状态、经营类型、未接触原因、业务进展、跟进与模拟完成。
- [字典演示数据](dictionaries.demo.json)：与页面分离；`DEMO_` 编码不进入业务接口或迁移。

## 1. 页面与操作

沿用现有 MASTER 的白底、石墨文字、操作橙 #C64C1C、系统中文字体。只在主操作和选中项使用橙色；已合作用浅绿底与深色文字，不铺大面积深绿。48px 以上点选区、52px 主按钮，内容留白 20px，区块间用浅灰隔带。无状态 emoji、无装饰性插画、无距离数字。

一张滚动表单，固定底部“完成拜访”。顺序如下：

| 区块 | 首屏/展开内容 | 交互 |
| --- | --- | --- |
| 门店摘要 | 名称、地址、到店时间、时长、录音状态 | 录音收成一行，点击看详情；正常时不堆提示 |
| 门店现状 | 营业状态、经营类型 | 读取最新门店资料；整行打开底部单选面板 |
| 本次沟通 | 已沟通/未接触、接待人、合作进展 | 未接触时隐藏接待人和合作填写，改问原因 |
| 现场照片 | 门头照缩略图、已完成/所需张数、拍照 | 按本次规则决定必填数量；原型示例为 1 张 |
| 后续跟进 | 下步行动、跟进时间、补充记录 | 无安排可留空；更多经营信息默认收起 |

不新增强制多步骤向导。接待人直接选已有联系人，可在底部面板新增，保存后回到原表单。草稿按租户/账号/拜访隔离；已知内容不重复填写，服务端同步与本机草稿分别显示真实状态。

原型初始值是“已有资料带入”的示例，不是新门店的默认答案。正式实现禁止默认选“营业中”“有意向”“已合作”，未知时允许“待核实”。新增业务必须由销售选择进展，不能默认生成中意向。

### 必填标识与提交校验（用户补充确认）

用户要求：必填项标清楚，点击完成时未填项提示准确。所有当前生效的必填项在标题后标橙色 `*`，不只依赖颜色；条件不生效时隐藏星号和相应校验。

| 条件 | 必填项 | 漏填提示示例 |
| --- | --- | --- |
| 所有拜访 | 营业状态、经营类型确认、沟通结果 | 请选择营业状态；请选择经营类型，暂不清楚可选“暂未核实”；请选择已沟通或未接触 |
| 本次规则要求照片 | 按规则数量的现场门头照 | 请拍摄 1 张门头照；或还需拍摄 1 张门头照（按真实缺额） |
| 已沟通 | 本次接待人、合作情况 | 请选择本次接待人；请添加有进展的业务，或选择“暂无合作意向” |
| 添加了某项业务 | 每项业务的合作进展 | 请选择高德的合作进展，不使用笼统“请选择合作意向” |
| 未接触 | 未接触原因 | 请选择未接触原因 |
| 暂时停业 / 已停业 | 核实依据 | 请填写暂时停业的核实依据 |
| 经营类型 / 未接触原因选“其他” | 简短说明 | 请填写其他经营类型；请填写其他未接触原因 |
| 填写了下步行动或跟进时间之一 | 另一项同时填写 | 请选择跟进时间；请选择下步行动 |

“待核实/暂未核实”是明确选择，不能视为漏填，也不能把未知强行判成营业中。有条件必填的说明输入框只在相应条件下出现。补充记录、业务需求、更多经营信息仍为选填。

点“完成拜访/提交结果”时一次校验全部当前生效字段，保留所有输入；滚动并聚焦第一项错误，在字段下显示准确原因，其他漏填位置也标出。底部可点击简短汇总“还有 N 项必填信息未完成”，不连续弹多个 toast。修正后立即清除该字段错误；切换“未接触”时清除已隐藏接待人/合作字段的错误，草稿内容保留但不随未接触结果提交。

正式实现需区分“未拍照”和“照片待上传/上传失败”，后者提供继续上传/重试，不能让用户重复拍摄。录音与定位属于系统采集/规则核验，失败提示对应恢复动作，不能列作销售漏填字段。前端校验通过后进入防重提交，后端字段错误继续定位到具体字段；版本冲突、权限、网络失败保持独立提示。

设计总览底部提供“演示必填校验”，可查看多个漏填项、滚动定位、逐项修正的效果；该按钮只存在于设计画布，不进入销售 App。

## 2. 营业状态与经营类型

### 营业状态

复用 `CRM_STORE_BUSINESS_STATUS`：营业中 / 暂时停业 / 已停业 / 待核实，保留 OPEN / TEMP_CLOSED / CLOSED / UNKNOWN 稳定编码。它独立于公海私海、合作历史和营业时间。

- 正常营业、暂停营业、永久停业是门店事实。没开门可能只是没到营业时间，不能自动标记已停业。
- 暂停/已停业需要简短依据，可引用本次门头照片和实际核实记录；待核实不覆盖已有的确定状态，只保留本次观察待核实。
- 当销售修改并提交时，自动维护 CRM 统一门店档案，因此私海门店列表/详情同步可见，不另建“私海门店信息”副本。
- 点击选项只改草稿；成功提交后再同步，避免未完成拜访误改门店状态。
- 停业核实仍可保存这一次拜访，后续新作业沿用停业限制。门店已经处于停业状态而无法开始拜访时，继续使用 CRM 门店状态核实入口，不能靠放宽到店门禁解决。

### 经营类型

复用 `STORE_BUSINESS_TYPE`，建议单选“主导经营类型”：

| 建议显示名 | 判断边界 |
| --- | --- |
| 商业娱乐 | 日常休闲、付费娱乐是主要业务 |
| 竞技赛事 | 以竞技训练、赛事承办和比赛组织为主 |
| 培训教育 | 以课程教学、教练培训为主 |
| 综合经营 | 多种业务并重、无法确定主业；不是懒得判断的默认项 |
| 其他 | 字典尚未覆盖，补简短说明 |

未知时保留空值，表单提供“暂未核实”，不强迫编造答案；若本次选择已核实，才写回档案。原型用星号表示需作出选择/确认，正式实现不能因此把未知排除在外。

“自助/有人值守”“连锁/独立”属于经营方式，不与上述类型混在一个下拉里；可作为后续经营画像的选填字段。`CRM_STORE_TYPE` 已被 V47 定义为行业大中小类，不能借它保存竞技/培训等经营类型。

## 3. 合作进展：业务独立，保留高/中/低

不建议把“合”塞进高/中/低同一个意向枚举：已合作是关系状态，意向是转化判断。界面使用“已合作”全称，读起来清楚；数据分别保存。

推荐页面展示：

```text
合作进展                         ＋添加业务
高德                              高意向 ›
零售                              已合作 ›
```

选高德、零售、周边、鹰眼等业务后，各自点选高/中/低/暂无意向或已合作。底部面板中“合作意向”和“已开展合作”分组展示。选择有意向或已合作必须关联具体业务，允许多项业务。同一家店可零售已合作、高德高意向，不能用单一门店总状态覆盖。

- 意向继续使用 `CUSTOMER_INTENTION_LEVEL` 的 HIGH / MEDIUM / LOW / NONE；按业务存储，不删除现有语义。
- 合作状态复用 `CUSTOMER_COOP_STATUS` 的有效标准项，不新增 `intentionLevel=COOPERATED` 魔法值。
- 业务复用 `BUSINESS_LINE` 当前有效标准项及别名映射。现存迁移已合并“鹰眼业务”“城市零售代理”同义项，实施前必须查有效字典，不凭显示名重新造 AMAP/RETAIL 等业务编码。
- “零售”等短名应在字典展示属性或经过业务确认的命名中维护；App 不写名称映射数组。
- 销售确认“已合作”形成带来源、时间和采集人的业务关系观察。正式合作客户/成交/业绩仍使用实际订单、合同或业务开通事实；不得凭此次点选改变成交统计和合作客户池。
- 已有系统合作事实自动带入。销售不能在这张拜访表内撤销系统确认的合作；合作终止走原业务流程。
- 当前总体意向字段保留历史含义，不把各业务意向自动取最大值回写。旧记录只有总体意向时展示“历史整体意向”，具体业务未知，不自动补齐。
- 尚未沟通时不要求填意向。已沟通但无任何业务意向，可确认“暂无合作意向”，不强迫勾选业务。

## 4. 私域运营：采什么，什么时候采

| 信息 | 建议要求 | 价值 / 数据归属 |
| --- | --- | --- |
| 本次接待人、角色、是否参与决策 | 已沟通时关联接待人；不认识姓名可记录角色/未获取姓名 | CRM 联系人；不要把接待人自动等同老板或决策人 |
| 电话、企微建联情况 | 已有自动带入；本次新获信息再补 | 电话存在联系人，企微正式关系由实际绑定/同步判断；口头自报独立标注 |
| 具体业务、意向或已合作状态 | 有进展时必选对应业务 | 用于运营按业务分组，见上节 |
| 核心需求与当前阻碍 | 选填一句话 | 先用短文本，不为未确认业务发明几十个标签 |
| 下步行动和跟进时间 | 有约定时填写；高意向建议填，首版不强制 | 同步现有跟进/待办链路，不建第二个任务系统 |
| 台桌数量、现用品牌/供应商 | 更多经营信息，选填 | 需求量、替换机会；仅本次核实的字段更新 |
| 自助/有人值守、连锁/独立、营业时段 | 后续画像字段，先复用已有资料 | 按经营方式独立建模，字典维护；不每次拜访重填 |

不要每次要求采集营业额、身份证、执照、精确预算等。确有开户/合同需要时进入对应业务流程。不要让本次表单承担全面门店调查。

建议将现有强制长文本“拜访记录”调整成“补充记录（选填）”。结构化信息足够时由后端形成可审计摘要，异常状态/其他原因仍需短说明。这是拟变更业务口径，当前原生页面的“记录必填”尚未修改。

## 5. 独立自动离店距离

已确认当前实现：管理后台开关文案、Sales `autoDepartureContext` 和自动结束校验均复用 `checkInRadiusMeters`；App 收到该范围进行离店监测。需要整条链路同时改，不能仅在后台加一个输入框。

| 管理项 | 方案 |
| --- | --- |
| 到店范围 | 保留现有规则 |
| 离店自动结束 | 保留开关 |
| 自动离店距离 | 新增独立规则值；开启时必填；不得小于到店范围。建议可填范围先沿用现有 1–5000 米，扩大需另评估 |
| 连续确认与精度 | 保留当前精度校验、连续确认及定位中断恢复逻辑，不因新增距离而删去防漂移处理 |

原型 500 / 800 米仅示例，不替用户确定正式默认值。既有规则缺新字段时按旧到店范围继承，保持行为；新版本明确保存独立值。

新字段贯穿管理后台表单、发布校验、Sales 版本模型/持久化、CRM 保存的规则快照、自动离店上下文和后端判定。沿用已有 `visit-policy.uts` 与 Sales 共享缓存，不另建页面规则缓存；发布产生新版本，进行中的拜访继续旧快照。权限与适用范围仍实时核验。

**自动结束只结束现场计时和录音，不等于拜访结果已提交。** 若表单未填完，保留草稿并展示“已自动结束，结果待补充”，底部变“提交结果”。材料上传独立重试，不伪造已上传、已核验或有效拜访。定位丢失/低精度时不自动结束，保留手动完成。销售页不出现距离数字。

## 6. 字典、数据和缓存的落地合同

### 字典先行

1. 先盘点当前租户生效项与 canonical 别名，形成字典差异清单；已执行迁移不改写。
2. 通过 Foundation 现有管理能力或新增版本迁移补齐/规范必要字典项，再开放页面。不把原型 JSON 当生产字典。
3. 编辑选项用 `/api/v1/business-settings/dictionaries/effective`；历史显示用 `/resolve`，保留已停用历史值。页面从响应读取名称、排序、可用性，不内置“兜底选项数组”。
4. 营业状态复用 `CRM_STORE_BUSINESS_STATUS`；经营类型复用 `STORE_BUSINESS_TYPE`；业务复用 `BUSINESS_LINE`；意向、合作复用现有两本字典。沟通结果/未接触原因/下步行动先检查同义字典，无现有时再新增。
5. 按业务读权限开放所需白名单字典，不能为销售授予字典管理权限。Foundation 当前并未自动为本次全部字典开放销售权限，需实际验证 IAM/Foundation 权限链。
6. 显示选项是字典，影响工作流的稳定编码仍需要领域校验。字典增一个“营业状态”不意味着无需代码即可改变停业限制。

### 保存与回写

- Sales 是拜访结果/现场证据单一写者，CRM 是门店/联系人/经营画像单一写者，Foundation 是字典单一写者。App 不直连数据库、不中转三次独立保存来伪装原子成功。
- 结果保存原始观察：门店状态、依据、经营类型、每业务意向/合作观察、接待人、跟进；关联 tenantId/storeId/visitId/captureId/actor/time/policyVersion/字典代码。
- 可在 Sales 原结果事务内写入既有 outbox，投递 CRM 领域命令/事件，或复用现有具备重试回执的跨服务流程。实施时按项目已有机制选一种，不新造消息框架。
- CRM 校验租户、当前归属/权限、期望 revision、有效字典及事件幂等，再更新统一门店并记录前后值、核实依据和来源拜访。不能绕过当前 `crm:store:status-write` 授权。
- 自动回写与人工修改冲突时不静默覆盖；保留拜访观察并提示重新确认，或根据已有版本策略处理。待核实/空值不清空确定事实。
- Sales 保存成功但 CRM 尚未回写时，保持可重试同步状态，不能显示“门店信息已更新”。全部回执完成后失效门店详情、公海/私海/合作查询与附近列表缓存，检查现有版本键或事件失效路径。
- 业务进展按 `(tenant_id, store_id, business_line_code)` 维护最新视图，拜访内保留逐次观察历史；实体归属、正式表名、索引与旧字段演进在实施前按现有库表再确认。字段先落领域模型，不能把所有信息塞入拜访备注。

### 读取与性能

- 规则沿用现有预加载与版本缓存。字典使用账号/租户隔离的统一读取模块，合并重复请求并预加载；原生端当前没有可直接复用的通用字典服务，需要补齐，而不是把 Web Vue 实现拷贝成 UTS。
- Foundation 查询若新增缓存，复用 `shared-cache`，覆盖字典修改、启停、合并别名、租户覆盖后的版本提升与提交后失效；不能只加 TTL 而遗漏写入路径。
- 有有效缓存先显示，后台检查版本；冷启动仅相关字段处于加载态，其余资料可读，失败可重试。没有选项不允许假装保存成功。
- 经营画像/业务进展与现有现场资料并行加载，优先已有聚合接口或批量数据，不让新字段把刚优化的入口恢复成串行请求链。新旧耗时都以同设备记录验证。

## 7. 实施边界与验收清单

本轮仅设计原型与方案。尚未修改 App 页面、后台表单、业务服务、权限、数据库及线上字典，没有编译或真机验收新方案。

实施顺序：字典盘点与业务口径 → 规则/采集结果/CRM 回写接口及版本迁移 → 原生页面与后台表单 → 定向测试、三端编译、真机验收。

必须覆盖：

- 多业务不同合作状态、无意向、未接触、暂未核实；旧整体意向展示不被改写。
- 字典停用、改名、租户覆盖、别名合并、权限不足；历史可读，新选不可用项不能提交。
- 门店回写成功、版本冲突、权限撤销、重复提交、跨服务失败重试；所有相关缓存更新。
- 离店距离独立生效、新旧规则版本、误差与连续确认、后台/锁屏/断网恢复；自动离店后草稿与材料保留。
- 首次/再次进入耗时、账号切换、提交防重、上传失败、键盘、安全区、大字号、375px 与横屏。

## 8. 设计依据与已读源码

UI UX Pro Max 检索命中 Flat Design，采用低装饰、明确层级和触控反馈；自动推荐的营销落地页结构、蓝绿配色、拉丁字体不适用，未覆盖 MASTER。补充采用表单标签、必填标识、提交反馈；“conditional fields”没有直接命中条件展示规则，按技能通用原则和实际表单设计。Vue forms 命中通用 Web 库建议，但本工程是 uni-app x，不据此引入 VeeValidate/FormKit。已读 pro-rules 和 quick-reference §1–§3。
